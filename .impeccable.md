## Design Context

### Status and decision

**Audience confirmed by owner, 2026-09-22:** players aged 10–14, with parents
supporting. **Owner selected A — Clubhouse on 2026-09-22.** After challenging
repeated green defaults, the owner explicitly selected **cobalt blue + warm
coral, with neutral surfaces** as Golazo's default. Default green is not approved;
this is not a portfolio-wide green ban.

The approved implementation is the bounded player post-training journey below.
Club colors remain separate personalization on identity geometry, with readable
foregrounds. They do not tint every surface or override functional contrast.

### Primary job

Finished training → log it quickly → understand progress → leave encouraged.
Design for short, mobile-first visits after football training, including a
parent's phone. Supporting parents are not an audience for surveillance or
comparison with other children.

### Personality and healthy motivation

Encouraging, capable, personal. Effort matters; rest and missed sessions are
normal. No guilt, shame, streak anxiety, fabricated urgency or compulsory return.
XP acknowledges a recorded activity, not football ability, health or worth.
Celebrate a meaningful completion once; never turn every tap into a reward.

### Historical comparison (not final production evidence)

- **A — Clubhouse:** belonging through a fictional club identity, an original
  jersey/crest, expressive type, a clubhouse noticeboard and earned celebration.
  The original navy/mint proposal was superseded by the owner's cobalt/coral
  decision above. No public
  team feed, fabricated teammate activity, ranking or social pressure.
- **B — Training companion:** focused athletic typography, restrained surfaces,
  a linear training journal and one clear next action. Ink, chalk and lime are
  a proposal, not an approved palette. Progress is explained rather than scored
  against other players.

Both use the same synthetic Alex / Northbank FC U13 training scenario and
interactive states. Neither copies commercial football-game or language-app
assets. Neither transplants Rosette's serif/plaster identity.
See [the original rendered directions and verification](docs/design-directions/training-20260922/README.md).
Independent concept review found no significant issues within concept scope.
Those screenshots remain history, not evidence for the production implementation.

### Journey and states

Player Clubhouse entry; optional scheduled-training prefill; editable log;
native field validation; atomic local persistence of entry and real age-scaled
XP; retained draft and explicit retry on local-storage failure; completion with
comprehensible progress and an explicit finish. Cloud sync remains separate:
local success must never be labelled server confirmation. No artificial save
delay, synthetic reward or inactivity XP is part of the real app.
Date, type, duration, energy, mood, focus areas and notes reflect existing
`TrainingEntry` fields. Rest/missed-day reassurance links to the existing schedule;
it does not create a record. Existing matches/goals/activities remain available
through "More football"; coach and mentor dashboards are not redesigned.

### Constraints and verification

Native keyboard controls, visible focus, comfortable targets, reduced motion,
WCAG 2.2 AA as the accessibility target, 320/390px mobile and desktop reflow,
200% text enlargement, separately measured native browser zoom, and long-string
stress checks. Test the source-stamped production build with synthetic
localStorage fixtures and intercepted auth/API calls in fresh browser contexts.
Never use real children's profiles. Original concept data remains ephemeral.

Production uses existing React, CSS and react-i18next with all six existing
locale resources. No component framework, dependency change or storage-schema
change. Existing fonts/components remain; the scoped Clubhouse CSS carries
the approved identity. No new production performance budget is approved:
measure the actual built request graph/payload and do not claim field Web Vitals.

### Approval boundary

Backend/auth/storage schema and XP/age-tier rules stay unchanged. The existing
CI gains the reviewed pinned design gate and a nondeploying manual build; only a
fresh production evidence receipt and independent review can satisfy its UI-PR
gate. No production receipt exists yet. Parent coordinates remote validation,
independent review, PR and deployment; the implementer stops at the candidate.
Automated checks and agent review are not representative-user testing.
